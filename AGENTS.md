# Правила роботи з trade-system

- Не змінювати стек без явної вказівки: ASP.NET Core 10 / C# 14, EF Core 10 / Npgsql, PostgreSQL 18, React 19 / TypeScript / Vite, MUI, TanStack Query, React Hook Form / Zod, REST / OpenAPI, ASP.NET Core Identity / HttpOnly cookie, Serilog, xUnit / PostgreSQL Testcontainers, Docker Compose / Caddy.
- Зберігати modular monolith: Domain не залежить від інших шарів; Application залежить від Domain; Infrastructure реалізує контракти Application; Api є composition root.
- Не додавати зайві таблиці та поля. Кожна зміна схеми має бути потрібна погодженому функціональному slice.
- Не зберігати дані, які однозначно обчислюються з первинних даних.
- Не вводити cached stock, cached debt, cached balance, cached cost.
- Не додавати microservices, CQRS framework, Redis, Kafka, MongoDB.
- Кожен наступний функціональний slice має мати integration tests із реальним PostgreSQL через Testcontainers.
- Усі бізнес-правила повинні виконуватися на backend. Frontend-валідація служить лише для UX.
- Product Code: blank/null/whitespace при CREATE генерується backend як P000001…P999999, спільно для GOODS/SERVICE у межах Organization. CREATE/UPDATE беруть org-scoped transaction advisory lock перед Code query та Product row locks; використовують наявний UNIQUE (OrganizationId, Code). Manual Code trim/max 128, duplicate → 409 PRODUCT_CODE_EXISTS; UPDATE потребує непорожнього Code. Frontend не прогнозує код, показує відповідь backend; Barcode та старі codes автоматично не змінювати.
- Batch створюється лише при першому POST рядка закупівлі; UNPOST його зберігає. ProductId рядка з Batch незмінний. SERVICE не може бути рядком закупівлі.
- Залишки та резерви рахуються через звичайний `v_stock_balance`: physical із StockMovement, reserved із активних рядків не видалених DRAFT SaleInvoice, SupplierReturn, StockTransfer та WriteOff, available = physical - reserved. Не створювати StockReservation або кешовані баланси.
- Усі зміни stock/reserve виконувати транзакційно під спільними впорядкованими блокуваннями Batch. PUT/POST продажу, SupplierReturn, StockTransfer або WriteOff виключає лише власний reserve; залишок не може бути від’ємним. Помилка — `INSUFFICIENT_STOCK`.
- Не дублювати ProductId/OrganizationId у Batch чи StockMovement або дату руху в StockMovement. Продажі — лише UAH, без нових валютних полів або currency logic.
- PriceType належить організації; GOODS використовує BatchPrice, SERVICE — ProductPrice. Ціни мають складені ключі без дубльованого OrganizationId чи ProductId у BatchPrice.
- UnitCostUah обчислюється тільки через звичайний v_batch_cost: базова ціна закупівлі після знижки й курсу + частка POSTED direct Expenses на одиницю. Розподіляти за вартістю активних purchase lines, без проміжного округлення. Не зберігати cost snapshot або PurchaseCostAllocation; не змінювати BatchPrice при зміні Expenses.
- Початкові BatchPrice створювати лише для новостворених Batch під час POST закупівлі, за активними PriceType та їх DefaultMarkupPercent. Наявні ціни не переписуються при повторному POST, UNPOST чи зміні закупівлі/націнки; UNPOST їх не видаляє.
- RecommendedUnitPrice визначає backend із вибраного PriceType та зберігає як snapshot рядка документа. Зміна прайсу або звичайний PUT не переоцінює збережений рядок; нова рекомендація потрібна при новому рядку чи явній зміні Product/Batch/PriceType. Пропущений UnitPrice нового рядка = рекомендація, наявного рядка без зміни вибору = збережена фактична ціна.
- UnitPrice нижче рекомендованої потребує явного дозволу; рівна/вища дозволена без нього. API adapter визначає дозвіл через sale.change_price із активних ролей користувача. Не робити заборону постійним доменним інваріантом. HTTP body/headers не надають дозволів.
- Counterparty та його DefaultPriceType належать поточній Organization. Purchase/Sale використовують лише існуючих контрагентів своєї організації. Системних контрагентів фізично не видаляти; не створювати автоматично «Роздрібного покупця» без окремого bootstrap завдання.
- SettlementMovement — єдине джерело взаєморозрахунків. Purchase POST створює один негативний рух, Sale POST — один позитивний, OPENING_STOCK не створює. UNPOST видаляє рух документа в тій самій транзакції зі складом; повторний POST не дублює його.
- Баланс = SUM(SettlementMovement.Amount) за Counterparty/Currency через v_counterparty_balance. BalanceAfterMovement обчислювати window SUM у query окремо для кожної валюти. Не зберігати balance/debt/advance/paid/status або line/document totals.
- Суми рахувати з активних рядків після header discount без округлення кожного рядка. Кінцевий Amount округлювати до 4 знаків; BaseAmountUah закупівлі = округлений Amount × ExchangeRate з округленням до 4 знаків. UAH для sale settlement — 00000000-0000-0000-0000-000000000980, без таблиці валют.
- Грошовий баланс = SUM(MoneyMovement.Amount) через v_money_account_balance. Мінус дозволений при POST та UNPOST; не додавати перевірку достатності коштів або AllowNegativeBalance. У MoneyMovement не дублювати CurrencyId/OrganizationId/MovementDate/Balance.
- MoneyAccount має одну валюту; після посилання документа/руху її не змінювати. MoneyDocument використовує спільний Document.DocumentType MONEY_RECEIPT / MONEY_PAYMENT / MONEY_TRANSFER; operation_type та ефективний курс переказу не зберігати.
- SETTLEMENT receipt створює негативний SettlementMovement, SETTLEMENT payment — позитивний. Transfer, OWNER, OPENING_BALANCE та null Purpose не створюють settlement. Не зберігати settlement-реквізити без SETTLEMENT; transfer не має SETTLEMENT purpose. Курс UAH = 1.
- Money POST/UNPOST атомарні для обох журналів і блокують Document FOR UPDATE; посилання на рахунки/контрагента перевіряються в межах організації. Не додавати PaymentAllocation, Obligation або Advance tables.
- Expense використовує спільний DocumentType EXPENSE та лише погоджені реквізити, Amount numeric(20,4), ExchangeRate numeric(20,6). Текст — у Document.Comment/InternalNote, без Description. POST створює тільки негативний SettlementMovement; оплату оформлює окремий MoneyPayment SETTLEMENT.
- ExpenseCategory — дерево довільної глибини в межах організації, без циклів. Серіалізувати зміни дерева transaction advisory lock організації; не обмежувати глибину довільною константою.
- Direct Expense посилається тільки на POSTED PURCHASE_INVOICE поточної організації з ненульовою вартістю; zero-total → INVALID_PURCHASE_EXPENSE_ALLOCATION. Тримати shared lock закупівлі до commit. Невилучений Expense, включно з DRAFT, блокує UNPOST закупівлі → DOCUMENT_HAS_DEPENDENCIES. DRAFT Expense видаляється логічно, POSTED спочатку UNPOST.
- Не реалізовувати товари, закупівлі, продажі, склад, користувачів або бізнес-міграції без окремого завдання.
- CustomerReturn має тільки DocumentId, SourceSaleInvoiceId, StorageLocationId; рядок — Id, CustomerReturnId, SourceSaleLineId, Quantity, RefundAmount. Counterparty/Product/Batch/UnitPrice брати із source sale, не дублювати. Source — лише POSTED SaleInvoice своєї організації. Склад повернення має вже використовуватися в purchase/sale цієї організації, без нового довідника.
- CustomerReturn limits обчислювати SUM тільки POSTED невилучених returns. Серіалізувати POST/UNPOST повернень через SourceSale Document FOR UPDATE до перевірки лімітів; далі Product/Batch locks у погодженому порядку. DRAFT не резервує stock або return limits. RETURN_QUANTITY_EXCEEDED для GOODS, RETURN_AMOUNT_EXCEEDED для фінансового ліміту SERVICE.
- GOODS RefundAmount backend рахує із фактичного UnitPrice та original header discount, ручне значення заборонене. Округлення до 4 знаків; остання кількість отримує залишок net amount, сума не перевищує net. SERVICE дозволяє частковий refund > 0 та Quantity = 0 для фінансової компенсації. Refund facts зберігаються в рядках; returnable/refundable totals — тільки query.
- CustomerReturn POST створює позитивний stock у тому самому Batch лише для GOODS і один негативний UAH settlement за сумою refund; MoneyMovement та нових Batch немає. UNPOST видаляє обидва журнали атомарно після StockRules.RequireSafeRemoval. Невилучений CustomerReturn, включно з DRAFT, блокує Sale UNPOST → DOCUMENT_HAS_DEPENDENCIES. DELETE тільки logical DRAFT.
- Cookie auth: HttpOnly; Secure у production; перед додаванням mutating auth endpoints забезпечити CSRF-захист. Не замінювати cookie токенами в localStorage.
- SupplierReturn: header лише DocumentId, SourcePurchaseInvoiceId, StorageLocationId; рядок лише Id, SupplierReturnId, SourcePurchaseLineId, Quantity. GOODS only; source — POSTED PURCHASE_INVOICE своєї організації, не OPENING_STOCK; Batch/Product/Counterparty/ціна/валюта/курс визначаються через source.
- DRAFT SupplierReturn резервує stock через v_stock_balance поряд із sales, без StockReservation. Зміни source/рядків/складу блокують old/new Batch; перевірка виключає лише власний збережений reserve. POST/UNPOST різних SupplierReturn серіалізуються source Purchase Document FOR UPDATE, stock writers — спільними Batch locks.
- SupplierReturn quantity <= purchased мінус SUM POSTED невилучених SupplierReturns та available у вибраному складі. POST створює negative stock і positive settlement із original price/discount/currency/rate, без direct Expenses або v_batch_cost. Unit cost/BatchPrice не змінюються. UNPOST видаляє журнали атомарно й перевіряє відновлення DRAFT reserve; DELETE лише logical DRAFT звільняє reserve. Будь-який невилучений SupplierReturn, також DRAFT, блокує Purchase UNPOST → DOCUMENT_HAS_DEPENDENCIES.
- Не комітити секрети, `.env`, згенеровані збірки та node_modules. Оновлювати lockfiles разом із залежностями.
- StockTransfer має лише DocumentId, FromLocationId, ToLocationId; рядок — Id, StockTransferId, LineNo, BatchId, Quantity. From/To різні та вже використовуються у purchase/sale організації; Batch належить організації через source purchase. Product/Organization у рядках не дублювати. LineNo та Batch у документі унікальні.
- DRAFT StockTransfer резервує тільки FromLocationId у спільному v_stock_balance. Усі зміни беруть Document FOR UPDATE та впорядковані old/new Batch locks; PUT/POST виключає лише власний збережений reserve. POST створює -Quantity у From і +Quantity у To для того самого Batch, без нових Batch, settlement чи money рухів.
- StockTransfer UNPOST перевіряє projected physical/reserved у всіх зачеплених Batch/locations, видаляє обидва рухи та відновлює reserve у From в одній транзакції. Використаний/зарезервований destination stock не можна зробити недостатнім → INSUFFICIENT_STOCK. POST idempotent, номер ST зберігається після UNPOST. DELETE лише logical DRAFT звільняє reserve; historical validation без окремого завдання не додавати.
- Перевіряти `dotnet build backend/Trade.slnx`, `dotnet test backend/Trade.slnx`, `npm --prefix frontend run lint` та `npm --prefix frontend run build`. Integration tests потребують Docker.
- WriteOffReason має тільки Id, OrganizationId, Name, ExpenseCategoryId, Active; category тієї самої організації. WriteOff — лише DocumentId, StorageLocationId, WriteOffReasonId; рядок — Id, WriteOffId, LineNo, BatchId, Quantity. Не дублювати Product/Organization/UnitCost/Amount; один Batch і LineNo лише раз у документі.
- DRAFT WriteOff резервує stock у спільному v_stock_balance поряд із sale/SupplierReturn/StockTransfer. Власний reserve виключати при PUT/POST, old/new Batch блокувати за ID. POST idempotent, створює тільки negative stock, WO-номер лише вперше; не створювати Expense/SettlementMovement/MoneyMovement/Batch. UNPOST атомарно повертає stock і DRAFT reserve після projected stock validation. DELETE тільки logical DRAFT.
- v_write_off_cost — звичайний VIEW: SUM(WriteOffLine.Quantity × current v_batch_cost.UnitCostUah), категорія через WriteOffReason. Cost/amount snapshots або cached totals не вводити. Історична вартість змінюється разом із direct Expenses/current cost; це очікувано. Report query має scope через Document.OrganizationId, posted-only звіт фільтрує Document.Status; VIEW відсікає deleted документи.

- Identity V1: користувач належить одній незмінній Organization; Username глобально унікальний, назва ролі — у межах Organization. Counterparty користувача та призначені ролі тільки його організації. Користувачів не видаляти фізично; використовувати Active.
- RequestContext визначати тільки з валідованої Identity cookie; X-Actor-Id та X-Organization-Id ніколи не є джерелом контексту, також у Development. Test scheme та bypass CSRF можуть існувати лише в Trade.Tests.
- Права = union permissions активних ролей; обчислювати на кожний запит, без effective cache у User/cookie. Нові API обов’язково додавати до централізованої permission mapping; собівартість/прибуток потребують cost.view/profit.view.
- Unsafe cookie requests, включно з login/logout, вимагають X-CSRF-TOKEN із GET /auth/csrf. Після login отримувати новий token. Logout відкликає security stamp; inactive користувач не може використовувати стару сесію.
- Development seed лише за явним DevelopmentSeed:AdminPassword та IsDevelopment; жодного production-пароля чи bootstrap production через dev seed. Не додавати claims/login/token/MFA таблиці без відповідного функціонального завдання.

- Frontend auth: current user лише в TanStack Query; credentials:include, HttpOnly cookie, in-memory CSRF, жодних auth tokens у localStorage/sessionStorage. 401 очищає приватний query/mutation cache і переводить на login; 403 показує forbidden без втрати сесії.
- Frontend API prefix /api (Vite/Caddy strip prefix), browser document routes повинні отримувати SPA, також після reload. Не проксіювати /products та інші UI routes до JSON API для HTML navigation.
- Navigation і direct-route UI guards використовують одну конфігурацію permissions; frontend не замінює backend authorization. Dashboard не повинен вигадувати фінансові значення або обчислювати balances/cost/profit із неповних API.
- Frontend перевірки: npm --prefix frontend run lint, npm --prefix frontend test, npm --prefix frontend run build. Business backend regression tests залишаються обов’язковими. MUI theme tokens у src/theme; не додавати інший UI framework.
- Для Secure cookie за Caddy обробляти X-Forwarded-Proto лише від стандартних loopback або явно налаштованих ReverseProxy:KnownNetworks. Не очищати список trusted proxies, щоб довіряти довільним Internet requests.

- Product UI: /products, /products/new, /products/:id; приховані Attributes не очищати при PUT; Category вибирати зі спільного дерева, старе невідоме значення зберігати до явної зміни. Без raw GUID/JSON у UI, physical delete, prices/stock/batch/editor/import/scanner функцій без окремого завдання.
- Unit — Id, OrganizationId, Name, Active; без Symbol або conversion rules. Довідники Unit/Category мають UI у /directories. Відомі Unit/Category іншої Organization заборонені на Product create/update; старі зовнішні GUID зберігати сумісними. Пошук Product лише через серверний search/ItemType/Active, без зміни Product domain model.
- Counterparty UI: /counterparties, /counterparties/new, /counterparties/:id. IsSystem не редагувати у формі та зберігати при PUT; ролі незалежні. Використовувати існуючі backend permissions, не додавати нових прав для UI. Взаєморозрахунки читати лише з settlement API, окремо за валютами, без frontend SUM або cached balance. Показувати Document.Number замість GUID. Без довідника валют не вгадувати ISO-коди невідомих CurrencyId. Sales/Purchase/Expense/Money tabs залишати placeholders до окремих завдань.
- Purchase UI: /purchases, /purchases/new, /purchases/:id. PUT з Version та незмінними Id рядків; Product із Batch не редагується навіть після UNPOST. Перед POST зберігати dirty форму тільки після confirmation; failed save блокує POST. POSTED read-only; POST/UNPOST/DELETE через наявні backend rules, без ручних stock/batch/price змін у frontend. Поточний UnitCostUah лише з v_batch_cost і за cost.view; totals тільки derived, не додавати колонки.
- StorageLocation — Id, OrganizationId, Name, Active; універсальний довідник /directories/storage-locations без seed/адрес/поділу магазин-склад. Старі зовнішні StorageLocationId лишаються сумісними; відомий склад іншої Organization заборонений у Purchase. Нової таблиці валют без окремого завдання не додавати.

- Purchase audit: версія редагованої форми належить її початковим даним, фоновий query refresh не замінює її. Успішно створену чернетку не створювати повторно після failed/uncertain POST. Кількість у партіях брати з source purchase line, не називати її stock balance. Закупівельні витрати — лише read через існуючий expense API та expense.view, без Expense CRUD у Purchase UI.
- Sale UI: /sales, /sales/new, /sales/:id; GOODS із Batch, SERVICE без Batch/stock queries. FIFO-підбір — тільки UI recommendation із available-batches; backend остаточно перевіряє stock і permissions. excludeSaleId дозволений тільки для власного невилученого DRAFT, власний reserve виключати лише в його збереженому складі; базові physical/reserved/available не змінювати, повертати окрему AvailableForDocument.
- Sale форма зберігає версію початкових даних та Id рядків, не надсилає RecommendedUnitPrice або totals. Збережений snapshot пріоритетний над поточним прайсом; пропущена ціна наявного незміненого рядка зберігає actual. Перед POST зберігати dirty форму після confirmation; failed save блокує POST, успішно створений DRAFT не дублювати після failed POST. POSTED read-only, DELETE лише DRAFT.
- Sale cost/profit — тільки backend read queries через поточний v_batch_cost, окремі cost.view/profit.view; profit DTO не повинен повертати CurrentCost без cost.view. Не обчислювати собівартість/прибуток на frontend і не зберігати snapshots/totals. Не додавати Return/Payment/Print/POS UI без окремого завдання.
- Stock UI: GOODS only, Product+Location або Batch+Location читаються через v_stock_balance, без persistent frontend copies чи нових balance/reservation tables. Running balance і джерела резерву — backend queries; include всі активні DRAFT Sale/SupplierReturn/StockTransfer/WriteOff. Batch не має Active; ручного створення Batch немає.
- Stock ціни: retail/wholesale PriceType вибирає користувач явно; не визначати їх за довільним sort/name та не seed нові типи автоматично. Для різних цін партій показувати діапазон. CategoryId фільтрувати через product_categories; показувати повні шляхи категорій своєї Organization, не вигадувати назви старих невідомих GUID.
- Stock read API приховує cost/purchase valuation без cost.view на server; profit.view не потрібен. Transfer/WriteOff UI використовує тільки існуючі write endpoints та operation permissions, Version/Id рядків і confirmation. Own reserve виключати тільки для власного DRAFT відповідного типу в збереженому source location. Не створювати Batch/Expense/Settlement/Money через складський frontend.
- Money UI читає balances через backend/v_money_account_balance, не блокує negative balance при POST/UNPOST і не вводить insufficient funds rule. Receipt/payment SETTLEMENT мають окремі реквізити; OWNER/OPENING_BALANCE не є income/expense та не створюють settlement. Transfer effective rate лише derived, не передавати/не зберігати окремо.
- Money форми зберігають Version baseline; confirmation → save dirty → POST. Failed save блокує POST, успішно створений DRAFT не дублювати після failed POST.
